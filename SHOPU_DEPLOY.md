# ShopU deployment notes

## Render deployment

The repository now includes `render.yaml` with two services:

1. `shopu-web` — the Django web service and Mini App.
2. `shopu-telegram` — the persistent Telegram bot worker.

The web service exposes `/health/` for Render health checks and `/` redirects to `/miniapp/`. Render automatically supplies `RENDER_EXTERNAL_HOSTNAME`, and ShopU derives the Mini App URL from it when `MINIAPP_URL` is left empty. Set `MINIAPP_URL` only when using a custom domain.

Core Render environment variables:
- `DJANGO_SECRET_KEY` — generated by the Blueprint.
- `DJANGO_DEBUG=false`
- `DATABASE_URL` — persistent PostgreSQL URL (Supabase or Render Postgres).
- `TELEGRAM_BOT_TOKEN` — BotFather token.
- `TELEGRAM_BOT_USERNAME` — optional, used for referral links.
- `MINIAPP_URL` — optional; defaults to `https://RENDER_EXTERNAL_HOSTNAME/miniapp/`.
- `SHOPU_AUTO_RELEASE_HOURS=6`
- `SHOPU_CRON_SECRET` — long random secret used only by the maintenance scheduler.

The Telegram worker receives the web service's `DJANGO_SECRET_KEY`, `DATABASE_URL`, bot credentials, and hostname through the Blueprint, so those secrets do not need to be copied manually to the worker.

Telegram security:
- `TELEGRAM_INIT_DATA_MAX_AGE_SECONDS=3600` (optional)

Paystack:
- `PAYSTACK_SECRET_KEY=sk_live_...`
- `PAYSTACK_CALLBACK_URL` (optional)

The Paystack secret key stays server-side. Never put it in the Mini App JavaScript.

## Paystack setup

1. Create/activate your Paystack account.
2. Put the live secret key in Render as `PAYSTACK_SECRET_KEY`.
3. Set the Paystack webhook URL to:
   `https://YOUR-DOMAIN/api/payments/paystack/webhook/`
4. Paystack signs webhook requests; ShopU verifies the signature before processing.
5. ShopU also verifies the transaction with Paystack before crediting the wallet.
6. The wallet is credited only once for a successful payment.

The existing `Payment` model is now a real provider-payment record rather than a generic placeholder.

## Vendor verification

Vendor verification is optional. Sellers can list and sell without verification.

Admins control the verification process in Django Admin:
- enable/disable the program
- require identity verification
- require business verification
- require payment-history verification
- require transaction-history verification
- set minimum completed transactions

A verified/trusted badge is only shown after the configured process is satisfied and an admin grants the status.

## Referrals

Admins control the referral program in Django Admin:
- enable/disable referrals
- commission percentage
- number of eligible completed transactions per referred user

The default limit is 10. Commission is awarded to the referrer when a referred user's order is completed, and each referred user can generate rewards only for the configured number of their first completed transactions.

Referral links use Telegram deep links:
`https://t.me/YOUR_BOT?start=ref_CODE`

## Background maintenance and scheduling

The Telegram bot is a persistent Render background worker. It is separate from the Django web process so Telegram polling cannot block or crash the web service.

ShopU's business maintenance remains event-driven and database-backed. Business events create pending jobs and can immediately request a GitHub Actions `repository_dispatch`.

Add these Render environment variables for immediate event dispatch:
- `SHOPU_GITHUB_ACTIONS_TOKEN`
- `SHOPU_GITHUB_REPOSITORY=OWNER/REPOSITORY`

Add these GitHub repository secrets:
- `SHOPU_URL=https://YOUR-DOMAIN`
- `SHOPU_CRON_SECRET=<same value as Render>`

The workflow in `.github/workflows/shopu-maintenance.yml` listens for `repository_dispatch` and also runs every 15 minutes as a safety fallback. **cron-job.org should be configured as the primary 1-minute scheduler**, calling the same authenticated maintenance endpoint; GitHub Actions remains the immediate repository-dispatch path plus the 15-minute safety fallback. Empty queues are returned immediately without processing.

The database lease plus per-job dedupe key, retry/backoff and lock make duplicate triggers safe. This avoids paying for a Render background worker. GitHub documents `repository_dispatch` as an external event that can trigger a workflow.

## Database and static files

Run:
- `python manage.py migrate`
- `python manage.py collectstatic --noinput`

Use Render Postgres for persistent data. Do not deploy the development SQLite database.

## Development-only funding

`/api/test-deposit/` remains development-only and must never be enabled as a production funding method.
